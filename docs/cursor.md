# Cursor SDK sessions

Pi Desktop's **Settings → Cursor SDK** is a client for the official [Cursor CLI ACP interface](https://cursor.com/docs/cli/acp). It is a separate agent engine, not a Cursor-to-model-API bridge. Cursor manages its model context, tools, authentication and account limits; Pi sessions are unchanged.

## Setup

1. Enable **Cursor SDK** in Settings and paste a user API key from **Cursor Dashboard → API Keys**. No manual CLI installation or `agent login` is needed for key authentication.
2. Leave **Advanced → Cursor CLI executable** blank. Pi Desktop downloads a pinned official package, verifies its size/SHA-256 and installs it under its own `cursor-sdk` directory. Local installation lives under the app's user-data directory; SSH installation lives under that connection's Pi install root. Managed SDKs are prepared on the first Cursor model check/session that needs them, without blocking ordinary Pi server connections.
3. Choose a machine and click **Check connection**. Download/upload progress is shown. The model picker opens with the account's advertised models; choose the few you want to see in conversations and press **Done**. No inference prompt is sent. A healthy installation is reused without downloading again. Allow at least 1 GB free for setup.
4. Start a **new** conversation, choose **Cursor CLI**, and use the normal model menu, which lists only your chosen models. Existing Pi conversations stay Pi even if the new-conversation draft selects Cursor. The password field clears after a successful save; blank saves preserve the key and **Remove key** clears it. Without a saved key, an existing CLI login remains supported.

Pi never runs the upstream shell installer: that installer overwrites global `agent` aliases. Managed setup leaves `~/.local/bin/agent`, Grok and shell profiles untouched. The old generic `agent` default now selects managed setup. Advanced custom paths must identify a complete official `cursor-agent` runtime package; identity checks happen before launching any process with a key. Cursor's self-updater is disabled for these launches so runtime updates stay under Pi's control.

**Existing 0.1.28/0.1.29 users:** if `agent` pointed to a different program, those versions may have passed the saved Cursor key in that program's environment. Update and rotate that key as a precaution; the desktop cannot establish whether another program read or stored it.

The key is encrypted in the desktop's existing Keychain-backed secret store, separately from settings. Only key presence is returned to the renderer. Model discovery sends it on stdin; sessions use the relay's private boot record. The adapter removes the boot variable and supplies `CURSOR_API_KEY` to Cursor, never a command-line flag or a desktop-written key file on the SSH host. Supplied API keys/auth tokens select the official `AGENT_CLI_CREDENTIAL_STORE=memory` mode: Cursor does not need an unlocked remote macOS login keychain and keeps authentication ephemeral. The encrypted desktop key is supplied again when a session restarts; login fallback without a supplied key retains the CLI's normal credential store. Pi provider keys and Electron's `ELECTRON_RUN_AS_NODE` are not passed into Cursor. The host's proxy and CA settings are (`HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY`, `NO_PROXY` in either case, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`), as for any program run there: an SSH host that reaches the internet only through a proxy cannot reach Cursor without them. Known API keys are redacted from CLI error diagnostics. Cursor controls its own child tools and credential handling.

Saving/replacing/removing a key does not interrupt active work. The next idle model lookup or prompt restarts the Cursor adapter with the updated credential and resumes the same native session/history. An attempt to refresh credentials while a turn or question is active asks you to finish or stop it first. No VMISS service or reverse-engineered provider endpoint is required.

## Conversation behavior

- Cursor marks supplied API keys/auth tokens or an existing CLI login authenticated during startup. Pi does **not** call ACP `authenticate(cursor_login)` automatically: that method is interactive browser login, not API-key validation. Actual account/key validity is checked by Cursor when services/models are requested. Protocol failures now identify the method, error code and safe detail instead of hiding everything behind “Invalid params”.
- Replies and tool activity use the normal conversation display; generated files use the same local/SSH file pane and terminal.
- Desktop-managed Cursor CLI launches use official `--force` (the `--yolo` alias) for all local and SSH ACP sessions. This allows commands and file changes without repeated approval, except where explicitly denied by Cursor policy. It does not change standalone CLI settings, override deny rules, or automatically approve MCP servers. Existing running sessions adopt it when their Cursor process is restarted.
- Any remaining tool permission requests, questions and plan approvals appear in the conversation. Always Allow forwards the exact advertised option ID; Cursor owns its scope and persistence, rather than the desktop guessing a broad approval policy. Unknown blocking client methods fail explicitly rather than hanging indefinitely.
- Stop sends ACP `session/cancel`; an unresponsive CLI is terminated after a bounded grace period. A new message interrupts the previous turn through the normal desktop mechanism.
- The existing relay owns the adapter and Cursor process, so detaching or quitting the desktop does not itself stop the conversation. Transcript projection and the native Cursor session ID are saved separately under `agent/cursor-sessions`. Reopening uses `session/load`, never a new session disguised as the old one.
- Conversations always run in Cursor's **Agent** mode. Ask/Plan are not offered; a session that the CLI opens in another mode is switched to Agent before the first prompt, and requests to leave it are refused.
- Reasoning effort uses the same control as Pi's, under the message box. A new conversation already offers the efforts Cursor lists for the chosen model (its default first; an effort you chose before is reused when the model offers it). Models that split reasoning into a thinking switch and a level (Claude) show one list: Off, then the levels. Cursor stores one effort per model for all of its sessions, so each conversation records its own and restores it when its CLI restarts or its model changes. Fast and other model parameters appear only when the live session advertises them.
- Cursor's ACP reports no token usage, so Context shows an estimate (`~`) of the conversation's own text and tool output, without a context window or percentage. Cursor's system prompt, rules and compaction are not visible to the desktop. Usage reported by a future CLI replaces the estimate.
- While the new-conversation screen has Cursor CLI selected, the desktop starts that conversation in advance: in the chosen folder, or for No folder in a provisional `new-chat` directory, with the draft's model and effort, and draft changes are applied to it as you make them. Cursor needs several seconds to start and a server round trip to open a session or change a setting; done ahead, the first message only publishes the conversation, and the next one is started ahead right after. An unused one stops after ten minutes, or when the Cursor key or executable changes, and leaves no files behind.
- An idle Cursor conversation keeps its CLI running for an hour (Pi: 20 minutes), because a restart delays its next reply by several seconds plus a history reload.
- Composer text and image drafts are retained per conversation while switching sessions or opening settings. Drafts remain in memory, not across app restarts.
- The conversation model menu lists only the models chosen in Settings, so a large Cursor catalogue does not flood the picker. The full list is loaded once, cached on disk and shown immediately next time; **Refresh** replaces it explicitly. Model changes during a running turn are rejected.

## Limits

Pi's goal loop, Pi subagent controls, history editing and fork are not Cursor ACP features and are disabled for Cursor sessions. Cursor controls its own compaction. Usage and context counts are not fabricated from elapsed time or text length when the CLI does not report them. Cursor todo/subagent/image extension notifications are not promoted into fake Pi task records. Tools may still have side effects even if a turn is cancelled.

Requires ACP protocol version 1, session loading and model selection. The managed package version is pinned in `core/cursor-release.mjs` and updated through desktop releases; custom installations remain the user's responsibility. Offline tests verify account/model behavior with a mock peer, while a separate GitHub CI probe downloads the real official package, initializes ACP over pipes and checks the pre-authenticated session-listing route with a synthetic invalid key. It never calls the interactive authentication method, creates a model session or sends an inference prompt; it does not validate a real account/key. Local/SSH desktop regression tests cover model menus, tools, permissions, cancellation and restart.
